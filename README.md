## Stages туршилт (5 → 30 → 100 → 0 VU)

Ачааллыг алхам алхмаар нэмэгдүүлж, дараа нь бууруулах ramping загварыг `script-stages.js`-д тодорхойлж, `results/run-stages.txt`-д гаралтыг хавсаргав. 80 секундын турш нийт 4198 хүсэлт илгээгдсэн бөгөөд p(95)=231.17ms, error rate 0.00% байв.

## SLO сонголт тайлбар

Алхам 2-т хэмжсэн анхны (5 VU, 1 минут) baseline p95 (229.61ms)-ийг SLO-гийн үндэслэл болгож авав.

SLO = baseline p95 (229.61ms) × 1.5 ≈ **344ms**

- `script-threshold-pass.js` → `results/run-30vu-slo-v2.txt`: `p(95)<344ms` threshold-той
  30 VU дээр ажиллуулахад **PASS** гарсан (бодит p95=230.64ms).
- `script-threshold-fail.js` → `results/run-100vu-slo-fail.txt`: FAIL кэйс харуулах
  зорилгоор санаатайгаар хатуу `p(95)<200ms` threshold тогтоож 100 VU дээр
  ажиллуулахад **FAIL** гарсан (бодит p95=230.99ms). Энэ нь бодит SLO биш —
  зөвхөн PASS/FAIL хоёуланг үзүүлэх зорилготой туршилт.

Дэлгэцийн зураг: `screenshots/threshold-pass.png`, `screenshots/threshold-fail.png`

## Дүгнэлт

1. Load тестийг зөвшөөрөлтэй дадлагын сайт test.k6.io дээр гүйцэтгэсэн бөгөөд
   бусад бодит вебсайт руу тест хийгээгүй.
2. VU тоо 5-с 100 болтол нэмэгдэхэд throughput шугаман пропорционалаар өссөн
   (7.58 → 45.16 → 150.09 req/s).
3. Бүх түвшинд error rate 0.00% байсан нь target сервер өгөгдсөн ачааллыг
   хүндрэлгүй даасныг харуулна.
4. VU 5-с 100 болтол нэмэгдэхэд p95 latency харьцангуй тогтвортой хэвээр
   байсан (229.61ms → 239.02ms), server-side хямралын шинж илрээгүй.
5. Stages ашигласан ramping тест (`script-stages.js`)-ийн үр дүн (p95=231.17ms)
   тогтмол ачааллын тестүүдийн үр дүнтэй нийцэж байгаа нь тогтвортой гүйцэтгэлийг
   баталгаажуулж байна.
6. Threshold-оо Алхам 2-т заасны дагуу 5 VU-гийн бодитоор хэмжсэн baseline
   дээр үндэслэсэн — зааврын жишээ тоог шууд хуулбарлаагүй.
7. options дотор stages болон vus/duration хоёуланг зэрэг ашиглаагүй тул
   тус тестүүд тус тусдаа зөв summary өгсөн.
8. `k6 run ... | tee results/...` команд ашигласнаар терминал дээрх гаралт
   болон файл руу хадгалагдсан гаралт хоёул ижил агуулгатай байлгав.
9. FAIL кэйсийг зориудаар хатуу threshold тогтоож гаргасан — энэ нь бодит SLO
   (344ms) биш, зөвхөн PASS/FAIL хоёуланг харьцуулж үзүүлэх зорилготой.
10. Цаашид илүү нарийвчилсан дүн шинжилгээ хийхийн тулд WebSocket, POST хүсэлт
    зэрэг илүү олон төрлийн endpoint дээр туршиж болно.
